## 一、实验目标与实际准备过程

本实验研究多核下共享数据的组织方式如何影响自旋锁竞争。原版页分配器将所有空闲页串在一条链表上；原版磁盘缓存用一把锁保护全局链表和引用计数。它们可以保证互斥，但无关请求也必须等待同一把锁。优化目标是在保持资源归属、引用和访问语义正确的基础上，使常见操作能够并行。

恢复继续实验时，原仓库处于 syscall 分支，并有用户已经暂存的 Lab2 修改。为保留这些工作，本次没有在原工作区切换分支或覆盖文件，而是在独立工作树中开展 Lab3。基准是 `lock-26-fall-v2` 对应的提交 `d7ad3766db44407fa6258df9e4366d8df5f6ed92`。允许提交的路径只有 `kernel/kalloc.c`、`kernel/bio.c` 和 `time.txt`，因此没有用修改测试、评分标准或增大缓存容量的方式改善成绩。

## 二、任务零：六道问题

### 1. 什么是内存分配器，它有什么作用？

内存分配器管理可用内存的申请与归还。这里研究的是内核物理页分配器，以 4096 字节为单位提供物理页，服务于用户内存、页表、内核栈和管道等。它管理内核结束地址向上按页对齐后至 `PHYSTOP` 之间的完整页，不是把全部 RAM 都当作空闲空间，也不是用户态的 `malloc()`。

### 2. 核心数据结构和主要操作有哪些？

空闲页的起始位置临时用作 `struct run`，其中 `next` 指向下一张空闲页；`freelist` 保存表头，锁保护链表关系。

- `kinit()`：初始化
- `freerange()`：逐页调用 `kfree()` 建立空闲集合
- `kfree()`：校验地址、填充垃圾值并归还一页
- `kalloc()`：摘取一页，成功返回地址，失败返回空指针

分配后页首恢复为可用数据，不另行分配链表结点。

### 3. 为什么每 CPU 一条链表能够减少竞争？

不同 CPU 的普通申请和释放访问不同锁及链表，可以并行执行。本地没有页时才访问其他 CPU 的链表，将高频竞争转移到较少发生的借页路径。各 CPU 的链表仍需加锁，因为其他 CPU 可能来借页。关闭当前 CPU 的中断只能稳定 CPU 编号，不能代替跨 CPU 的互斥。

### 4. 什么是磁盘缓存，它有什么作用？

磁盘缓存是文件系统与磁盘驱动之间的内存块缓存，保存磁盘块内容以减少重复 I/O，也为共享磁盘块提供统一的同步位置。同一设备的同一块只能对应一份缓存副本；缓存管理锁维护映射和引用，块自身的睡眠锁控制数据访问。

### 5. 为什么 struct buf 同时保留 prev 和 next？

原版采用双向 LRU 链表，两个方向的指针支持向前查找、从尾部挑选空闲块，以及在已知结点位置时常数时间摘除和移动结点。本实现保留这两个字段，用于桶内双向链表的摘除；它们本身不意味着仍然维护全局 LRU 次序。

### 6. 哈希桶为何减少争用，为何不能直接每 CPU 一份缓存？

不同块号分散到多个桶后，不同桶的查询与引用更新使用不同锁，查找范围也更小。若每个 CPU 独立缓存同一个块，可能出现两份可修改但内容不同的副本，破坏文件系统一致性。空闲物理页可以唯一划分给不同 CPU，磁盘块则必须按设备与块号维持统一身份。哈希冲突和未命中仍可能竞争，并不会完全消失。

## 三、页分配器：本地操作与批量借页

最终结构为 `kmem[NCPU]`，每个元素包括一把自旋锁和一条空闲页链表。

### 初始化与启动均衡

1. 先为全部元素调用 `initlock()`，锁名均以 `kmem` 开头，再执行原来的空闲区间遍历
2. 初始页先由执行初始化的 CPU 收入链表，再在 `kinit()` 内按 CPU 编号轮流分配到全部链表
3. 分配前清空原表头，每次先保存下一页再改写链接，使每页恰好进入一个列表，各列表页数差至多一
4. 此时其他 CPU 仍停在 `main()` 的 `started` 等待处，发布 `started` 前后的内存屏障保证初始化结果可见，所以这段启动过程不需要链表锁；运行期间的链表操作仍必须加锁

启动时均衡是为降低首次借页集中到启动 CPU 的竞争。`NCPU=8` 是内核支持上限，实际测试使用三核；借页遍历全部 `NCPU`，因此未启动 CPU 列表中的页仍可被使用，不会损失可分配内存。

### kfree()

- 保留对页对齐、内核边界和物理内存上限的检查，并保留填充值 `1`
- 随后执行 `push_off()`，读取 CPU 编号，持有对应锁将页面插入本地表头，释放锁后调用 `pop_off()`
- 因此，选择链表和完成插入之间不会因中断调度迁移到另一 CPU
- 填充操作发生在重新发布页面之前

### kalloc() 与批量借页

1. 同样先稳定 CPU 编号，在本地锁下尝试摘取表头
2. 本地为空时，先释放本地锁，再按循环顺序检查其他 CPU
3. 找到非空来源后，在来源锁下截取最多 **32 页**，把来源表头推进到截断位置，并断开该批次的尾指针
4. 释放来源锁后，这批页暂时由当前调用独占：第一张返回给调用者，其余页面在本地锁下接到当前链表
5. 成功页面最后填充 `5`，保留原版帮助发现错误引用的调试行为

选择批量借页是为了减少反复访问来源锁的次数；上限 32 控制单次遍历和持锁时间。这是局部策略参数，不改变物理页总量。一次借到多少取决于来源链表长度，不要求必须凑齐 32 页。

### 关键不变量

每张页要么属于某一条空闲链表，要么属于一次已摘除的私有批次，要么已经分配给调用者——这些状态互斥。

- 批次先在来源锁下整体摘除，再发布到本地，因此不会同时挂在两个链表中
- 并发借页者也必须取得来源锁，无法取走同一段
- 连接剩余页面时重新取得本地锁，避免覆盖其他 CPU 在此期间对本地链表的合法访问
- 整个借页路径同时至多持有一把 kmem 锁，不存在两个 CPU 各自拿着本地锁等待对方来源锁的环路
- 若遍历其他链表仍没有取得页面，则保持返回空指针的接口语义
- 初始化是否漏页、反复申请回收是否丢页，还需通过耗尽内存的测试验证

## 四、磁盘缓存：31 个桶与统一替换入口

缓存保留固定的 `buf[NBUF]`，其中官方 `NBUF=30`，没有添加额外的 `struct buf` 哨兵或扩大数据容量。新增 **31 个桶**，每桶只有锁和头指针。使用 `blockno % 31` 定位桶，实际命中仍同时比较 `dev` 和 `blockno`，不同设备的相同块号不会被误认作同一块。

初始时所有未分配身份的缓存块放在独立 free 链表中，暂不加入哈希表。这能避免初始化为零的设备号、块号被当成真实命中。free、环形游标和身份更换由 `bcache.evict` 保护；所有桶锁名称以 `bcache` 开头，能够被课程统计正确识别。

### 命中路径

`bget()` 持有目标桶锁查找。若找到目标块，先增加 `refcnt`，再释放桶锁并取得该块的睡眠锁。引用先于等待建立，因此即使其他进程暂时持有睡眠锁，替换者也不能回收这块缓存。`bread()` 继续在数据无效时读盘并置为有效；`bwrite()` 保留原来的持锁检查和写盘行为。

### 未命中路径

第一次查找失败后释放桶锁，再取得 `evict`，重新锁住目标桶并查找。重查是必要步骤：等待 `evict` 时，另一个请求可能已经插入同一目标。若不重查，两个原本都未命中的请求就可能各自创建副本。重查命中直接建立引用；仍未命中才进入分配与回收。

### 回收路径

1. 优先从 free 取出尚未使用的缓存块
2. 池耗尽后，从环形游标指向的位置扫描固定数组，每检查一个位置就推进游标
3. 持有 `evict` 时身份不会被其他替换者修改，再取得候选所在桶的锁检查 `refcnt`
4. 只有引用为零才能从旧桶双向链表摘除，并立即将引用设为一，作为当前请求的保留
5. 随后释放旧桶锁，在新桶锁下设置设备号、块号、`valid=0` 并插入表头

常态迁移先释放旧桶锁再取得新桶锁，即使两者是同一桶也不会重复获取同一把锁。迁移过程始终持有 `evict`，其他未命中请求不能同时插入新身份。这是环形扫描回收，不是带访问位的 CLOCK，也不是严格 LRU；游标分散扫描起点，释放操作不再维护全局最近使用顺序。

### 慢路径：全桶复查

独立审查发现，逐桶扫描一轮未发现空闲项，不能直接推断所有缓存同时被占用。例如，28 块始终被固定引用，A、B 两块交替占用；扫描者可能先看到 A 忙，随后看到 B 忙，却错过期间释放的块。

修复设计：在快速扫描失败后，保持 `evict`，按桶号从小到大取得全部 31 把桶锁，进行引用计数的一致复查。若发现零引用块，就摘除并预留；按反序释放全部桶锁。只有一致复查确认没有候选才报错。这条慢路径不改变普通命中和单桶回收的锁粒度。宿主确定性交错回归和最终 QEMU 测试均已验证下文列出的场景。

### brelse / bpin / bunpin

`brelse()` 先释放块的睡眠锁，再在桶锁下减少引用。其现有引用在递减前保证身份稳定，所以可以据块号定位所属桶。日志使用的 `bpin()`、`bunpin()` 也改为在对应桶锁下增减引用；遗漏这两个接口会使回收判断与日志保留状态不一致。

顺序可概括为：

- **页借用：** 来源锁 → 释放 → 本地锁 → 释放
- **缓存命中：** 桶锁 → 增加引用 → 释放 → 等待块睡眠锁
- **普通未命中：** evict → 单个桶锁 → 释放该桶锁 → … → 释放 evict
- **失败复查：** evict → 桶 0 → 桶 1 → … → 桶 30 → 逆序释放
- **缓存归还：** 释放块睡眠锁 → 桶锁 → 减少引用 → 释放

命中路径不会持有桶锁去等待 `evict`；未命中路径遵循 evict 在前、桶锁在后。普通路径至多持有一把桶锁，极慢复查统一按桶号升序获取，避免反向等待。缓存块只有在零引用时才可更换身份，正引用既涵盖使用者也涵盖已排队等待睡眠锁的请求。锁顺序说明用于排除设计层面的环路，实际测试则补充检查实现是否遗漏了同步步骤。

## 六、调试过程：从失败证据确定修改方向

### 6.1 先建立原版对照，再验证分阶段实现

原版的两个竞争测试失败，但完整正确性测试通过。由此确定需要改变的是共享状态的组织与锁粒度，不能通过改测试阈值、减少并发负载或增大资源总量解决问题。

单独优化 kalloc 的阶段使用原版 bio：

- 八把 kmem 锁的自旋均为零，`tot=0`，test1、test2 均通过
- 可分配页数为 **32499/32768**，50 轮耗尽与回收保持一致
- `kalloctest` 用时 **50.9 秒**；该阶段 `sbrkmuch` **5.3 秒**通过

分阶段测试用于缩小问题范围，最终结论仍以两个优化合并后的测试为准。

### 6.2 修复扫描过程中“空闲位置移动”的边界问题

逐桶检查并不是一个同时刻的快照。审查时构造了 28 块被固定引用、A/B 两块交替占用的情形：扫描者检查 A 时 A 忙；释放 A 后另一个 CPU 获取 B；扫描者再检查 B 时 B 也忙。于是逐项扫描可能都看到忙，却不能据此认定缓存整体耗尽。

为验证这一点，使用真实 `bio.c` 逻辑和 `buf.h`，仅移除内核 include，并在宿主测试中提供锁、睡眠锁、I/O 的替身，安排上述确定性交错。未增加一致复查时实际输出：

```txt
mode=race, exit=1
FAIL: bget: no buffers with A.refcnt=0 despite an available buffer
```

修复是在逐项扫描失败后按固定顺序取得全部桶锁，再检查一次引用计数。最终 31 桶实现的同一回归输出：

```txt
mode=race, exit=0
PASS: recycled A after shifting-free-buffer race; unique mapping,
      no locks held at sleep; max spinlock depth=32
mode=exhausted, exit=0
PASS: genuinely exhausted cache still panics with every buffer referenced
```

32 层自旋锁是 evict 加 31 把桶锁，只在扫描失败后的复查中出现。测试工具也根据最终源码的桶数配置锁检查数组，避免继续使用旧的 13 桶上限。这项定向测试只覆盖指定交错及真实耗尽场景，不替代多核 QEMU 中的文件系统测试。

### 6.3 13 桶版本性能未达标，改用 31 桶

初版采用指导书举例的 13 桶。合并测试中 `kalloctest` 和 `sbrkmuch` 通过，但 `bcachetest` test0 失败，累计 `tot=4681`；各 kmem 锁和 evict 的自旋都是零，竞争集中于桶锁，test1 仍通过。因此继续缩短 evict 路径不能直接解决这一轮观测到的主要竞争。

测试中的三个进程各读取自己的文件。检查当时镜像，三个文件的数据块区间为 **904–913、915–924、926–935**；按 13 取模，跨文件同桶的块对共有 **23 组**。每个块又被逐字节读取 1024 次，跨进程的进度差会使这些冲突反复发生。将桶数改为略大于缓存容量的质数 **31** 后，上述区间中跨文件同桶块对只剩一组。这说明增加的是锁和头指针元数据，并未增加固定的 30 个数据缓存块。

31 桶定向测试两项均通过，累计 `tot=0`，用时 **11.3 秒**。该解释针对当时镜像的访问分布；哈希冲突仍可能在其他工作负载中出现，31 并不是无冲突保证。

### 6.4 启动时页集中导致的竞争风险

后续一次新鲜启动复测又出现 `kalloctest` test1 失败：`kmem[0]` 自旋 **479**，其余 kmem 和 bcache 锁均为零，test2 仍通过。结合初始所有页集中在启动 CPU 的代码，这与其他 CPU 首次集中借页的热点一致；锁统计本身没有记录每一次争用的完整调用栈，不能据此声称已经追踪了所有发生位置。

据此把初始化完成后的空闲页均衡到各 CPU 链表，保留运行时的本地分配和 32 页借页机制。随后完成一次全套手动测试，以及原工作树、干净补丁恢复工作树各一次官方评分，三次新鲜启动的 `kalloctest` 均通过。这一过程也说明，单次零竞争输出不足以判断启动行为是否稳定。

任务中断后另有一次完整 usertests 日志只保留了开头，未输出结论；该次运行没有计入通过结果，也没有误记为内核测试失败。最终采用下面完整结束的运行记录。

## 七、最终测试环境与结果

环境为 RISC-V GCC 9.3.0、QEMU 4.2.1、Python 3.8.10。使用官方默认三核、128 MiB 内存、`NBUF=30`，未修改测试、评分脚本、Makefile、既有参数或工作负载。编译与评分前清理镜像，多个 QEMU 测试不同时运行，以免相互影响竞争统计。

- `#acquire()` 表示获取锁的调用次数
- `#fetch-and-add` 表示原子抢锁失败后的自旋次数，不直接等于等待时间
- `tot` 累加所有 kmem 和 bcache 类锁的失败次数，测试比较前后增量
- `kalloctest` 要求增量小于 10；`bcachetest` 实际代码要求小于 500，等于 500 不通过
- 这里的累计值与区间增量分别说明，不混用

## 九、如何自行复现与解释本实验

在 Linux 终端进入保留的源码目录并启动模拟器：

```bash
cd xv6-multicore-locking
make qemu
```

进入 xv6 shell 后，按指导书顺序执行：

```bash
kalloctest
usertests sbrkmuch
bcachetest
usertests
```

按 `Ctrl-A`，再按 `X` 退出 QEMU；回到 Linux 终端执行：

```bash
make grade
make clean
```

如果要检验交付补丁，可从原仓库创建另外一个尚不存在的临时目录，在干净标签上应用补丁后评分；不要把补丁重复应用到已经修改的源码目录。

```bash
cd xv6-oslabs-hitsz
# 在同一终端将 PATCH 设为历史补丁的绝对路径
git worktree add --detach /tmp/lab3-check lock-26-fall-v2
cd /tmp/lab3-check
git apply --check "$PATCH"
git apply "$PATCH"
make grade
```

整个实验的设计方法是先界定共享数据与不能破坏的约束，再决定锁保护的范围。对物理页而言，约束是唯一归属和总量守恒；对磁盘块而言，约束是统一身份、正确引用和数据访问互斥。随后把常见路径拆分到不同锁，把需要全局协调的借页和替换留在少数路径。最后用原版对照、分阶段检查、可复现的边界交错、完整回归与干净补丁验收来检验设计。遇到失败时先检查究竟是哪一类锁发生竞争、哪一项不变量受到影响，再作对应修改。
